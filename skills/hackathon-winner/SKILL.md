# Hackathon Winner

Help the user maximize the chance of shipping a memorable, honest, working submission. Winning is an optimization target, not a guarantee.

## Route the request

- For idea discovery, originality, sponsor fit, or choosing between concepts, read [references/idea-selection.md](references/idea-selection.md).
- For team setup, build sequencing, demo, submission, or post-hackathon follow-up, read [references/execution-and-submission.md](references/execution-and-submission.md).
- For end-to-end planning, read both.

## Core standard

Do not begin with generic AI-generated idea lists. First gather the hackathon theme, judging criteria, sponsor technology, time limit, team strengths, available proof surfaces, and recent adjacent projects. Use the user's idea bank and external research when available. AI is most useful for connecting inspirations, finding weaknesses, evaluating feasibility, and sharpening a seed—not inventing from a blank page.

An idea is a serious candidate only when it passes all of these gates:

1. **One-line clarity:** a stranger understands the product in one sentence.
2. **Visible pain or desire:** the problem can be explained in under 30 seconds.
3. **Technology removal test:** ask, “Could this product be built just as well without the organizer's technology?” If yes, reject or redesign it.
4. **Theme fit:** the central interaction embodies the stated theme rather than merely satisfying a track label.
5. **Early or unusually executed:** it is either a fresh capability or a familiar need executed with a domain advantage competitors are unlikely to match.
6. **One-minute proof:** the most important claim becomes visible during the first minute of the demo.
7. **Deadline feasibility:** one end-to-end path can work reliably before recording starts.

Treat unnecessary sponsor combinations as a liability. Every technology must perform a necessary job. Simple is preferable when it makes the sponsor technology shine more clearly.

## Required evaluation output

When comparing ideas, give a compact decision table covering:

- one-line pitch;
- target user and pain;
- organizer technology's indispensable role;
- theme alignment;
- novelty/earliness;
- domain advantage;
- first-minute demo moment;
- build risk within the actual deadline;
- strongest reason it wins;
- strongest reason it loses.

Rank candidates, recommend one, and state which candidates should be killed. Be blunt. Do not inflate weak concepts to preserve enthusiasm.

For the recommended idea, define:

- the smallest winning end-to-end slice;
- what is live, seeded, mocked, simplified, or deferred;
- the irreversible proof artifact: transaction, contract, signed receipt, generated world, physical event, benchmark, or independently checkable output;
- the fallback demo if a network, model, wallet, or sponsor API fails;
- the point at which feature work stops and demo preparation begins.

## Operating principles

- Prioritize the demo as part of the product. A well-demonstrated 90% build beats an invisible 100% build.
- Use domain knowledge as a moat, but avoid dependencies the team cannot learn safely within the deadline.
- Prefer a surprising interface or interaction when it clarifies the technology; avoid spectacle that hides a weak core.
- Distinguish workflow automation from a genuinely new capability. A workflow can still win only when its execution or domain depth is exceptional.
- Preserve the user's authorization boundaries. Researching and planning do not authorize registrations, submissions, deployments, purchases, messages, or repository changes.
- Encourage experimentation and learning. Do not frame a loss as wasted work or prize money as the only valuable outcome.
